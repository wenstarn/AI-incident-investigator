# Архитектура веб-приложения

Этот документ описывает интернет-магазин как работающую систему: его компоненты, данные, запросы и обычные зависимости. Названия сервисов и маршрутов соответствуют текущей реализации.

## Компоненты и связи

```mermaid
flowchart LR
    F[Frontend / Nginx :3000] -->|Отдаёт HTML, CSS и JavaScript| B[Браузер]
    B -->|HTTP :8001| U[User Service / FastAPI]
    B -->|HTTP :8002| O[Order Service / FastAPI]
    O -->|HTTP GET /users/{id}| U
    U --> P[(PostgreSQL :5432)]
    O --> P
    O -->|Кеш карточек товаров| R[(Redis :6379)]
```

| Компонент | Ответственность | Основные зависимости |
| --- | --- | --- |
| Frontend | Отдаёт страницу магазина и JavaScript; интерфейс пользователей, каталога и заказов | API User Service и Order Service вызываются браузером |
| User Service | Создание и поиск пользователей | PostgreSQL |
| Order Service | Каталог товаров, оформление и чтение заказов | PostgreSQL, HTTP к User Service, Redis для кеша |
| PostgreSQL | Постоянное хранение пользователей, товаров и заказов | Используется обоими бизнес-сервисами |
| Redis | Временный кеш имени и цены товара | Используется Order Service; не хранит первичные данные |

В локальном Docker Compose браузеру доступны Frontend по `http://127.0.0.1:3000`, User Service по `http://127.0.0.1:8001` и Order Service по `http://127.0.0.1:8002`. Внутри сети Compose Order Service обращается к `http://user-service:8001`, PostgreSQL — к `postgres:5432`, Redis — к `redis:6379`. Адреса и таймауты внешних зависимостей задаются конфигурацией сервиса. Frontend не является API-шлюзом: JavaScript отправляет запросы из браузера непосредственно в соответствующий сервис.

## Данные и границы владения

Оба бизнес-сервиса подключаются к одному экземпляру PostgreSQL, но используют отдельные схемы. User Service владеет таблицей `user_service.users` (`id`, `name`, уникальный `email`). Order Service владеет `order_service.products` (`id`, `name`, `price`, `stock`) и `order_service.orders` (`id`, `user_id`, `product_id`, `quantity`, `status`, `created_at`). Цена хранится как `numeric`, а не как число с плавающей точкой.

Order Service не читает таблицу пользователей напрямую. При создании заказа он проверяет `user_id` через HTTP-запрос к User Service. Поэтому `orders.user_id` — идентификатор пользователя без межсервисного внешнего ключа; `orders.product_id` ссылается на товар в собственной схеме Order Service. PostgreSQL остаётся источником истины для всех постоянных данных.

## Основные HTTP-маршруты

| Сервис | Метод и путь | Назначение |
| --- | --- | --- |
| User Service | `POST /users` | Создать пользователя; успешный ответ `201` |
| User Service | `GET /users/{user_id}` | Получить пользователя; неизвестный ID даёт `404` |
| Order Service | `GET /products` | Список товаров с `limit` и `offset` |
| Order Service | `GET /products/{product_id}` | Карточка товара; неизвестный ID даёт `404` |
| Order Service | `POST /orders` | Создать заказ; успешный ответ `201` |
| Order Service | `GET /orders/{order_id}` | Получить заказ по ID |
| Order Service | `GET /orders` | Список заказов; поддерживает `user_id`, `sort_order`, `limit` |

Интерфейс загружает каталог, позволяет создать или найти пользователя, оформить заказ и посмотреть историю заказов пользователя. При запуске стенда товары добавляются отдельным шагом подготовки данных. Бизнес-ответы о недоступной базе возвращают `503`. Для `POST /orders` недоступность User Service отображается как `502`, а превышение времени ожидания — как `504`.

## Как создаётся заказ

1. Браузер отправляет `POST /orders` в Order Service с `user_id`, `product_id` и `quantity`.
2. Order Service вызывает `GET /users/{user_id}` в User Service с ограниченным временем ожидания. Запрос не выполняется через Frontend и не читает таблицу пользователей напрямую.
3. После подтверждения пользователя Order Service проверяет товар и остаток в PostgreSQL. Уменьшение остатка выполняется условным запросом в одной транзакции с созданием заказа, чтобы параллельные покупки не продали больше имеющегося количества.
4. Сервис фиксирует заказ со статусом `created` и возвращает его клиенту. При отсутствии товара возвращается `404`, при недостатке остатка — `409`.

Order Service передаёт `X-Request-ID` в запрос к User Service. Это позволяет связать записи о клиентском запросе и межсервисном вызове.

## Чтение товара и роль Redis

`GET /products` читает список из PostgreSQL. Для `GET /products/{product_id}` Order Service сначала получает товар из PostgreSQL, включая актуальный `stock`, затем пытается прочитать кеш по ключу `product:{id}`. В Redis находятся только `name` и `price`; количество `stock` не кешируется. При отсутствии записи сервис кладёт эти поля в Redis с TTL, по умолчанию `300` секунд. При ошибке соединения с Redis чтение товара продолжает использовать данные PostgreSQL; ошибка кеша фиксируется в логах. Недоступность Redis поэтому не означает обязательную недоступность карточки товара.

## Проверки состояния и наблюдаемость

| Сервис | Путь | Что проверяет |
| --- | --- | --- |
| User Service | `GET /health` | Отвечает ли HTTP-процесс; базу не проверяет |
| User Service | `GET /health/db` | Соединение с PostgreSQL и простой запрос через сервис |
| Order Service | `GET /health` | Отвечает ли HTTP-процесс; зависимости не проверяет |
| Order Service | `GET /health/db` | Доступность PostgreSQL из Order Service |
| Order Service | `GET /health/redis` | Доступность Redis из Order Service |
| Оба сервиса | `GET /internal/stats` | Счётчики с момента запуска процесса и состояние пула БД |

При недоступной зависимости соответствующий `/health/db` или `/health/redis` возвращает `503`; обычный `/health` при этом может продолжать возвращать `200`. Контейнерные health checks используют именно `/health`, поэтому состояние `healthy` говорит о работающем HTTP-процессе, а не о безошибочности всех операций.

Оба FastAPI-сервиса пишут структурированные JSON-события в стандартный вывод; Docker сохраняет их как логи контейнера. Записи запросов содержат `timestamp`, `service`, `level`, `event`, `request_id`, HTTP-метод, путь, код ответа и `duration_ms`. Ошибки PostgreSQL, Redis и вызовов другого сервиса также логируются. `/internal/stats` даёт текущие счётчики запросов и ошибок, для Order Service — счётчики кеша и ошибок зависимостей, а также снимок пула SQLAlchemy. Счётчики находятся в памяти процесса и обнуляются при его перезапуске; это не хранилище исторических метрик.

## Как трактовать доступность

- Если `/health` отвечает, а `/health/db` возвращает `503`, проверять соединение с PostgreSQL и операции с базой именно из этого сервиса.
- Если User Service отвечает напрямую, но создание заказа не может проверить пользователя, проверять HTTP-связь и настройки зависимости со стороны Order Service.
- Если Redis отвечает напрямую, но кеширование в Order Service не работает, проверять доступность Redis из Order Service и адрес, который использует этот сервис.
- Если карточки товаров доступны при ошибках Redis, это ожидаемое поведение резервного чтения из PostgreSQL. Ошибки кеша всё равно полезны для объяснения задержек и снижения эффективности.
- Если `/health` обоих сервисов отвечает, но бизнес-запросы замедлены, сравнивать `duration_ms` и таймауты межсервисного вызова: простая проверка процесса не измеряет скорость бизнес-операций.
