# Агентская часть: одиночный агент и мультиагентная система

Пакет `services/investigator-agent` (`investigator_agent`) расследует инциденты магазина. Есть две системы:

- **single** — одиночный агент (baseline);
- **mas** — мультиагентная система: Координатор → специалисты → Критик.

Обе системы используют только восемь read-only инструментов из [`diagnostic-tools`](diagnostic-tools.md) и работают с любым OpenAI-совместимым API (chat completions + tool calling). Агентных фреймворков нет: цикл вызова инструментов — около 200 строк в `loop.py`, его легко читать и отлаживать.

Агенты **не имеют доступа к Incident Controller**. Им недоступны ID инцидента, управление Docker, shell, произвольный SQL и произвольные URL. Единственный вход — текст симптома.

## Быстрый старт

1. В `.env` (шаблон — `.env.example`) задайте LLM:

   ```sh
   LLM_BASE_URL=http://localhost:11434/v1   # Ollama; для OpenAI — https://api.openai.com/v1
   LLM_API_KEY=                             # пусто для локальных серверов
   LLM_MODEL=qwen3.5:4b
   LLM_EXTRA_BODY={"reasoning_effort":"none"}   # для qwen3.x в Ollama: без «размышлений»
   ```

   Облачный вариант через OpenRouter (код менять не нужно, API тот же):

   ```sh
   LLM_BASE_URL=https://openrouter.ai/api/v1
   LLM_API_KEY=sk-or-...                    # ключ с openrouter.ai/keys
   LLM_MODEL=deepseek/deepseek-v4.1-flash   # любая модель с поддержкой tools
   LLM_EXTRA_BODY=
   ```

   `LLM_EXTRA_BODY` подмешивает в запрос параметры конкретного провайдера. Для qwen3.x в Ollama отключение «размышлений» ускоряет ответ на CPU примерно в 50 раз (26 с → 0,5 с на коротком запросе).

   `make setup` не дописывает новые ключи в уже существующий `.env`: добавьте их вручную.

2. Проверить расследование без Docker на записанном мире инцидента:

   ```sh
   make agent-investigate SYMPTOM="POST /orders возвращает 502" REPLAY=INC-004
   make agent-investigate SYMPTOM="POST /orders возвращает 502" REPLAY=INC-004 SYSTEM=mas
   ```

3. На живом стенде (`make setup && make up`):

   ```sh
   make incident-activate ID=INC-006
   make agent-investigate SYMPTOM="GET /health/redis в Order Service возвращает 503" SYSTEM=mas
   make incident-reset
   ```

CLI печатает отчёт, список вызовов инструментов, число LLM-вызовов и токенов. Полный трейс со всеми сообщениями сохраняется в `investigations/` (флаг `--no-save` отключает сохранение).

## Agent Console: визуализация в реальном времени

```sh
make agent-console        # http://127.0.0.1:3010
```

Сервис `services/agent-console` (FastAPI и обычный HTML/JS) показывает работу агентов по ходу расследования:

- **Сбой.** Кнопки «Сломать» и «Починить» включают и сбрасывают INC-001…006 через Incident Controller. После включения консоль ждёт, пока сбой станет наблюдаемым, отправляет те же запросы «пользователей», что и live-харнесс, и подставляет симптом в поле.
- **Расследование.** Выберите систему (single или MAS) и симптом, затем нажмите «Расследовать». Консоль всегда работает с живым стендом: replay-миры остаются инструментом тестов и оценки и в презентационных прогонах не используются. Каждая роль получает свою дорожку: Координатор, Инфраструктура, Связность, Хранилища, Критик (для single — одна дорожка). В дорожках по мере работы появляются карточки:
  - 🎯 задание роли;
  - 💭 решение модели (текст и запрошенные инструменты);
  - 🔧 результат инструмента (зелёный — ok, оранжевый — проблема, красный — ошибка; полный ответ раскрывается);
  - 📋 план, 📝 выводы, 📄 черновик, ✅/❌ вердикт Критика.

  Мигающая точка в заголовке дорожки означает, что роль сейчас работает. Видно, что специалисты работают одновременно.
- **Итог.** Отчёт, метрики (инструменты, LLM-вызовы, токены, время) и, если на стенде включён инцидент (или стенд здоров), отметка «совпало / не совпало с правильным ответом». Правильный ответ видит только консоль, агенту он не передаётся.
- **Повтор сохранённых.** Каждое расследование из консоли сохраняется в `investigations/` вместе с потоком событий. Список проигрывает сохранённые **live**-расследования (из консоли, CLI и `eval-results/*-live`) со скоростью ×1…×100; прогоны на replay-мирах в список не попадают. Это удобно для презентации без ожидания медленной модели. Для старых трейсов без событий ход восстанавливается из переписки агентов.

Как это устроено: цикл агента (`loop.py`) и роли MAS сообщают о каждом шаге в `EventSink` (`events.py`). Консоль пересылает события в браузер через Server-Sent Events (`/api/investigations/{id}/stream`), а повтор отдаёт сохранённые события с исходными интервалами (`/api/traces/{id}/stream`). Логика агентов от консоли не зависит.

Консоль запускается на хосте рядом со стеком, как CLI, слушает только `127.0.0.1` и читает настройки из `.env`. `LLM_MODEL` нужно прописать в `.env`: `make` подключает этот файл, и пустое значение из него перекрывает переменную, заданную в командной строке. Токен Incident Controller хранится только на сервере консоли. Агенты по-прежнему получают лишь реестр read-only инструментов. Консоль отвечает только на запросы с `Host` = `127.0.0.1`/`localhost` (защита от DNS rebinding), а POST-запросы принимает только с заголовком `X-Agent-Console: 1`. Его отправляет сама страница, а чужой сайт отправить не может (защита от CSRF: вредоносная страница не сможет сломать стенд или потратить кредиты LLM).

## Отчёт

Обе системы возвращают одинаковый `IncidentReport`:

| Поле | Значение |
|---|---|
| `category` | `component_down`, `dependency_misconfiguration`, `dependency_slow`, `no_incident`, `unknown` |
| `component` | Где находится дефект: остановленный или медленный сервис либо сервис с неверной конфигурацией |
| `dependency` | Для `dependency_misconfiguration`: на какую зависимость указывает неверный адрес |
| `evidence` | Наблюдения со ссылкой на инструмент |
| `ruled_out` | Исключённые похожие причины |
| `recommendation`, `summary`, `confidence` | Текст на русском и уверенность 0..1 |

Пример: для неверного порта Redis в Order Service ожидается `dependency_misconfiguration / order-service -> redis`, а не `component_down / redis`.

## Одиночный агент

```text
symptom ──> [single-investigator: 8 инструментов + submit_report] ──> IncidentReport
```

Один цикл вызова инструментов (по умолчанию не больше `AGENT_MAX_STEPS=12` шагов). Агент завершает работу вызовом «финального инструмента» `submit_report`; его аргументы валидирует Pydantic. При ошибке валидации текст ошибки возвращается модели, и она может исправиться. Когда шаги заканчиваются, цикл принудительно запрашивает `submit_report`. Если отчёта всё равно нет, результат получает `category=unknown`.

## Мультиагентная система

```text
                      ┌──────────────────────────────┐
 symptom ──> Coordinator (triage)                    │
             get_service_status + dispatch           │
                 │ задачи                            │
     ┌───────────┼──────────────┐  параллельно       │
     v           v              v                    │
 Infrastructure Connectivity  Datastore              │
 status, logs   http, dep,    postgres, redis,       │
                config        metrics                │
     └───────────┼──────────────┘                    │
                 v наблюдения                        │
        Coordinator (synthesis) ──draft──> Critic ───┘
                 ^                            │  requested_checks
                 └────── approved? ───────────┘  (≤ MAS_MAX_REVIEW_ROUNDS)
                              │ да
                              v
                        IncidentReport
```

| Роль | Инструменты | Результат |
|---|---|---|
| Coordinator / triage | `get_service_status` | `dispatch`: гипотезы и 1–3 задачи специалистам |
| Infrastructure | `get_service_status`, `get_service_logs` | `submit_findings` |
| Connectivity | `check_http_endpoint`, `check_service_dependency`, `get_dependency_config` | `submit_findings` |
| Datastore | `check_postgres`, `check_redis`, `get_service_metrics` | `submit_findings` |
| Coordinator / synthesis | нет | `submit_report` (черновик) |
| Critic | нет | `submit_verdict`: approve или reject с запросом проверок |

Специалисты одного раунда работают параллельно (`asyncio.gather`). Синтез и Критик получают полный журнал сырых результатов инструментов, а не только пересказ специалистов. Это не даёт ошибке интерпретации одного специалиста незаметно попасть в отчёт.

### Почему здесь нужна MAS

Сценарии стенда специально образуют группы с **одинаковыми симптомами и разными причинами**:

- `POST /orders → 502` может означать, что User Service остановлен (INC-001) или что Order Service ходит на неверный порт (INC-004); `504` даёт медленный User Service (INC-005);
- рост ошибок Redis в Order Service может означать, что Redis остановлен (INC-002) или что в Order Service неверный адрес Redis (INC-006);
- при остановленном PostgreSQL (INC-003) User Service тоже начинает отказывать, и проба `order-service → user-service` выглядит как проблема User Service. Это настоящая каскадная «ложная улика».

Типичная ошибка одиночного агента — преждевременный вывод: увидев отказ соединения, он объявляет компонент «упавшим», не сравнив прямую проверку с проверкой изнутри сервиса. MAS отвечает на это структурно:

1. **Специализация и наименьшие привилегии.** У каждого специалиста 2–3 инструмента и короткий контекст. Модели проще правильно пользоваться инструментами, а ошибка одной роли не даёт ей доступа к чужим данным.
2. **Параллельность.** Независимые проверки (контейнеры, связность, хранилища) выполняются одновременно.
3. **Независимая проверка (Критик).** Критик не собирает данные, а проверяет дифференциальную диагностику:
   - заявлено «компонент остановлен» — была ли прямая проверка компонента;
   - заявлен «неверный адрес» — сравнили ли эффективную конфигурацию с прямой проверкой;
   - заявлено «медленно» — есть ли измерение задержки.

   Если нет, Критик возвращает задачу специалистам.

Цена MAS — больше LLM-вызовов и токенов. Поэтому главный результат — **измеренное сравнение**: даёт ли структура прирост точности и какой ценой. Для честности обе системы получают одну модель, одинаковые доменные знания (`prompts.py`) и один суммарный набор инструментов.

## Тестирование

| Уровень | Что проверяет | LLM | Docker | Команда |
|---|---|---|---|---|
| Unit | Механику: цикл, инструменты, лимиты, ошибки, роли MAS, раунды Критика, оценщик, харнесс | заглушка `ScriptedLLM` | нет | `uv run pytest services/investigator-agent/tests` (входит в `make test`) |
| Replay-eval | Рассуждения модели на записанных мирах INC-001…006 и `healthy` | настоящая | нет | `make agent-eval-replay REPEATS=3` |
| Live-eval | Всю систему на живом стенде через Incident Controller | настоящая | да | `make agent-eval-live REPEATS=1` |
| Replay fidelity | Что replay-миры совпадают с живым стендом по ключевым сигналам | не нужна | да | `make agent-replay-fidelity` |

### Кейсы

Симптом описывает то, что видит пользователь или алерт, и не называет причину. У INC-001 и INC-004 симптомы совпадают дословно, у INC-002 и INC-006 тоже. Кейс `healthy` проверяет ложные срабатывания. С флагом `GENERIC=1` все кейсы получают одинаковый расплывчатый симптом (сложный режим).

### Метрики

- **correct**: совпали `category`, `component` и (для misconfiguration) `dependency`.
- **partial**: совпала только категория.
- **grounded**: каждое доказательство ссылается на инструмент, который реально был вызван (защита от выдуманных наблюдений).
- **cost**: число вызовов инструментов, LLM-вызовов, токенов и время.

Итог: `eval-results/<время>-<режим>/summary.md` (таблица по кейсам и системам), `scores.json` и `investigations.jsonl` (полные трейсы каждого прогона).

`make agent-eval-report` собирает все прогоны из `eval-results/` в один файл `eval-results/REPORT.md`. В нём сводная таблица, сравнение MAS с одиночным агентом, список всех ошибок и подробности по кейсам. Все цифры вычисляются из `scores.json`. Чтобы положить отчёт в репозиторий, укажите путь: `make agent-eval-report OUT=docs/evaluation-results.md`.

```sh
make agent-eval-replay REPEATS=3                       # обе системы, все кейсы
make agent-eval-replay SYSTEMS=single CASES=INC-002,INC-006
make agent-eval-live REPEATS=1                         # разрушительно!
```

### Replay-миры

`evaluation/replay.py` описывает каждый мир маленькой моделью состояния: остановленные контейнеры, эффективные порты в Order Service, задержка User Service. Все ответы инструментов выводятся из этого состояния, поэтому они согласованы между собой при любых аргументах. Значения (статусы, типы ошибок, задержки, строки логов) измерены на живом стенде и согласуются с [incident-guide.md](incident-guide.md). Тест `test_replay_worlds.py` проверяет, что ключевые сигналы совпадают.

В логи приложений миры добавляют строки от бизнес-запросов, которые воспроизводят симптом. Live-харнесс отправляет такие же запросы после активации инцидента: 3 × `POST /orders` с несуществующим `user_id` (данные не меняются), `GET /products/1` или `GET /products`. Поэтому replay и live показывают агенту однотипные доказательства.

### Соответствие replay живому стенду

Режим `--mode fidelity` (`make agent-replay-fidelity`) не использует LLM. Для каждого кейса он активирует сценарий, воспроизводит симптом и выполняет один и тот же набор из 16 проб на живом стенде и в replay-мире. Затем сравнивает сигналы, на которые опирается агент: статус, тип ошибки, HTTP-код, достижимость, состояние контейнера, порт. Задержки и счётчики не сравниваются.

Измерения 18.10.2026 показали несколько особенностей стенда, которые учтены в мирах:

- Имя остановленного контейнера перестаёт резолвиться в сети Compose. Обращения сервисов к нему зависают на 3–8 с, тогда как прямые проверки с хоста отказывают мгновенно. Поэтому при INC-002 чтение карточки товара занимает около 12 с, а `POST /orders` при INC-001 возвращает 502 только через 8 с.
- `/health/redis` Order Service проверяет Redis по статическому адресу, поэтому при INC-006 (неверный runtime-адрес) он отвечает 200.
- Без PostgreSQL User Service отвечает 503 или зависает, поэтому проба зависимости из Order Service тоже деградирует.

Пробы, чья задержка близка к таймауту инструмента, могут давать разный результат в разных прогонах. После выравнивания миров последний прогон дал 1 расхождение из 112: `/health/redis` при INC-002 попеременно возвращает 503 или timeout.

### Live-харнесс

1. Отказывается работать, если уже есть активный инцидент или стенд нездоров.
2. Для каждого кейса: activate → ожидание, пока сбой станет наблюдаемым → воспроизведение симптома → расследование всеми системами и повторами → **reset в `finally`** → ожидание восстановления.
3. Токен контроллера читает только харнесс. Агенты получают лишь `ToolRegistry` с диагностическими функциями.

## Настройки

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_BASE_URL` | `http://localhost:11434/v1` | Адрес OpenAI-совместимого API |
| `LLM_API_KEY` | пусто | Ключ (не логируется и не попадает в трейсы) |
| `LLM_MODEL` | — | Обязательна |
| `LLM_TIMEOUT_SECONDS` | 120 | Таймаут одного запроса |
| `LLM_TEMPERATURE` | 0 | Температура |
| `LLM_MAX_RETRIES` | 2 | Повторы при 429/5xx и таймауте |
| `LLM_EXTRA_BODY` | пусто | JSON-объект с дополнительными полями запроса (параметры провайдера) |
| `AGENT_MAX_STEPS` | 12 | Лимит шагов одиночного агента |
| `AGENT_MAX_TOOL_OUTPUT_CHARS` | 6000 | Усечение длинных ответов инструментов (логи) |
| `MAS_MAX_REVIEW_ROUNDS` | 2 | Сколько раз Критик может вернуть задачу |
| `MAS_SPECIALIST_MAX_STEPS` | 6 | Лимит шагов специалиста |

Требования к модели: нужна поддержка tool calling. Маленькие локальные модели (≈4B) работают медленно на CPU и чаще ошибаются в аргументах. Для осмысленного сравнения лучше модель уровня 14B+ или облачная.

## Известные ограничения

- Результаты replay и live зависят от модели и недетерминированы. Используйте `REPEATS≥3` и сравнивайте доли.
- Replay-мир — модель, а не запись каждого возможного ответа. Аргументы, которых не было в реальных опытах, дают правдоподобный, но смоделированный ответ. Пробы на границе таймаута на живом стенде недетерминированы (см. «Соответствие replay живому стенду»).
- В INC-005 User Service сам пишет в лог событие `fault_injection_applied` («User lookup delayed by runtime fault»). Это артефакт стенда, облегчающий диагноз. Replay воспроизводит его так же, как live.
- Счётчики и логи на живом стенде зависят от предыдущих запросов, а replay даёт фиксированные значения.

## Дальнейшее развитие: RAG

Точки расширения уже заложены:

- **Документация и runbook'и.** Блоки `SYSTEM_TOPOLOGY`, `TOOL_NOTES`, `METHOD` в `prompts.py` — первые документы корпуса для Qdrant. Поиск по нему подключается обычным инструментом `search_knowledge(query)` в `ToolRegistry`. В MAS это естественно становится ролью **Knowledge-агента**, к которому Координатор обращается на этапе triage за гипотезами.
- **Память расследований.** CLI и харнесс сохраняют полные `InvestigationResult` (симптом, проверки, доказательства, диагноз). Из них получаются summary для поиска похожих случаев. Найденные случаи — гипотезы, которые всё равно нужно подтвердить инструментами.
- **Эксперимент.** К осям `--systems single,mas` добавляется `--rag on|off`; сравниваются точность, число вызовов и токены (architecture.md §12).
- **Предостережение.** `docs/incident-guide.md` содержит ответы на эти сценарии; индексировать его как есть нельзя. Память прошлых расследований при оценке кейса X должна исключать summary самого X (leave-one-out).
- Новые сценарии из architecture.md (`slow_sql`, `db_pool_exhaustion`, `wrong_db_password`) потребуют знаний, которых нет в базовом промпте. Именно на них RAG должен дать наибольший эффект.
